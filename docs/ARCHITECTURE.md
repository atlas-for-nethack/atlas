# Architecture

Atlas for NetHack is an offline macOS app containing the official NetHack 5.0.0 C engine, a narrow custom window port, a native Cocoa host, and a WebKit interface. It does not reimplement NetHack rules or depend on an external web service.

The engine runs as a child process. Its window port emits newline-delimited JSON events describing map glyphs, messages, status, menus and input requests. The native host polls nonblocking child pipes while a game is active, parses complete lines, and delivers batched events to the interface on the main thread. Input travels back over the child's standard input. The child process separates legacy C engine state from the UI and lets a new game start with a clean engine. It runs as the same user; this is neither App Sandbox nor a cross-user filesystem security boundary.

The native host uses only macOS frameworks, so users need neither Node nor Python nor Homebrew. WebKit is chosen for a polished, adaptable presentation with a small distributable; Cocoa owns the app lifecycle, menu bar, file picker and writable application-support directory. A pure SwiftUI renderer would avoid the bridge but make dense tile layout and rapid interface iteration harder without improving engine fidelity.

The app uses Atlas as its short name. Its bundle identifier and existing `NetHack Atlas/5.0` Application Support directory are retained so the rename preserves preferences and saved adventures.

Atlas does not write to its bundle during ordinary play. An ad-hoc signed bundle is not necessarily filesystem read-only; local integrity and trusted bundled resources are assumptions. Game resources are copied into a per-user 5.0 directory on first launch. Existing runtime resources are retained, so they can differ from a later bundle. The ordinary `ATLAS_DATA_DIR` environment override can select another writable directory. Engine launches explicitly bind `HOME`, `NETHACKDIR` and `HACKDIR` to the selected runtime. NetHack handles its native save format, recovery, bones and records. Hover descriptions come from the engine's look functions and do not advance time. The frontend does not infer actual identity from the hidden world state.

Beginner mode is an explicit Atlas starting-condition customization. Standard uses the original 5.0 runtime; Beginner uses its `Beginner/` child directory, including separate saves, bones, scores, locks and recovery checkpoints. The runtime namespace persists the mode without altering NetHack's save format. The native host supplies `ATLAS_PLAY_MODE` on every launch, including restoration, and identifies saves by both name and mode. The mode is not a mutable in-game switch. Imported tiles remain shared at the 5.0 root.

Explore is the upstream discovery mode, enabled with `-X` on both new-game and restore launches. It uses a third runtime, `Explore/`, with `EXPLORERS=*` authorized only in that runtime’s sysconf. Standard and Beginner configuration files are untouched. NetHack supplies the wishing wand, death-refusal prompt, keep-save prompt and non-scoring behavior. There is no additional engine patch for Explore and no Beginner supply grant. Startup recovers each of the three namespaces independently.

A maintained, fail-closed build patch adds one call in upstream `newgame()`, after normal role initialization and any rerolls, before the initial recovery checkpoint. The window port creates an unlocked, untrapped chest on nearby reachable floor, preferring the starting room and never covering stairs with the fixed Beginner supplies. It does not modify carried role equipment, attributes, combat, hunger or death rules, and the hook never runs during restoration. Object creation, container use, identification, map memory and save serialization use engine APIs. The supplied 1,000 gold is included in initial-money accounting, so picking it up does not count as earned gold for the separate Beginner score.

The bridge accepts known actions and checks that messages originate in a main frame with a file URL. Several action strings and fields have explicit limits; there is no universal bound on numeric values or menu collections. The handler does not itself check a Resources path prefix. Initial file loading, its Resources read scope, the navigation delegate and trusted bundle contents jointly restrict reachability. The navigation delegate rejects top-level navigation outside the local Resources tree. This is not a general prohibition on all WebKit network requests. Shipped resources use no remote scripts, fonts, analytics or sign-in. Engine output is inserted as text, not HTML.

Development playtests require `--playtest`, a resolved run directory beneath ancestors named `environment-playtests/runs`, metadata, an exclusive run lock, and a matching engine hash. That validation does not bind a direct launch to one particular checkout root. Selftests select disposable game data explicitly; automated engine tests construct a controlled environment and never substitute a player directory for fixtures.

The distributable targets macOS 13+ and bundles both Apple Silicon and Intel slices for the launcher, engine and recovery utility. Apple Silicon gameplay is exercised locally; Intel slices are compiled and structurally checked but have not been executed on Intel hardware. Developer ID signing and notarization are a distribution stage requiring an Apple Developer identity, outside the local ad-hoc build.

Acceptance covers a real new game, correct tile map, arrow movement, prompts and inventory, hover descriptions, save/restore, and an application bundle with no non-system runtime libraries. Complete NetHack playthrough coverage is not claimed.
